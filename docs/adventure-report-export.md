# Экспорт отчётов и резервное копирование

## Состояние доступа
Панель /gm/adventure-report/export по умолчанию работает с сохранёнными облачными черновиками текущего постоянного аккаунта. Дополнительная область all-drafts предназначена для администратора отчётов.
Сервер проверяет токен через Supabase Auth getUser, затем читает записи с user_id = auth.uid текущего пользователя.
Запрос использует публичный ключ и токен пользователя; service_role не используется. RLS остаётся обязательной.
Тестовые localStorage-черновики не экспортируются.

18.11.2026 в рабочем проекте подтверждены хранилище adventure_report_drafts и административное чтение.
Пользователь применил подготовленные миграции 20261117120000_adventure_report_drafts.sql и 20261118120000_adventure_report_read_admin.sql через SQL Editor; их результат проверен.
RLS владельца включена, анонимные сессии исключены, административное правило разрешает только SELECT.
Автотесты проверяют запросы и отказы на моделируемых ответах. Дополнительно выполнена read-only проверка роли authenticated с разными JWT claims непосредственно в рабочей базе.

Ограниченное административное чтение включено для выбранного пользователем постоянного аккаунта на семь дней.
Нельзя имитировать его service_role или пользовательским полем роли. Сам маршрут экспорта не меняет схему.
Текущая модель хранит один изменяемый черновик на аккаунт/приключение; история прохождений, отправка отчёта и защита статистики
от повторных игр требуют последующего согласованного этапа с run_id и историей ревизий.

## Фильтры и файлы
Фильтры: приключение, регион, ветвь, версия канона, статус проверки, даты последнего сохранения.
Даты включают оба края по UTC. Регион берётся из текущего реестра приключений, а не из исторического снимка канона.
Неизвестное приключение сохраняется с region = null. Строковые фильтры точные, с учётом регистра.
После подготовки все три скачивания используют один снимок; изменение фильтров требует повторной подготовки.

JSON: format_version, exported_at, scope = own-drafts, source_count, filters, report_count, warnings, reports.
Каждый reports[] содержит report_key, adventure_slug, region, saved_revision, updated_at, payload.
payload сохраняется без нормализации, включая неизвестные поля и ID карточек.
report_key — стабильный SHA-256 псевдоним аккаунта и slug, а не отдельное прохождение. Это не анонимизация свободного текста.

reports.csv: одна строка на отчёт; коды группы/кампании, редакция, канон, статусы, полный payload_json.
decisions.csv: одна строка на карточку; report_key, decision_id, решение, пояснение, исход,
наблюдаемый результат, сведения героев, открытые последствия, полный answer_json.
Связь таблиц по report_key. Для сравнения выгрузок используйте пару report_key + saved_revision.
CSV: UTF-8 BOM, запятые, CRLF, поля в кавычках. Формулоподобные значения получают начальный апостроф для безопасного открытия
в таблицах; оригинал остаётся в JSON. Для точного восстановления используйте JSON.
Неполный ответ (count не совпал с числом записей), дубликаты и повреждённые основные поля останавливают всю выгрузку.
Текущий лимит 1000 защищён проверкой полноты; при росте модели выше лимита потребуется серверный согласованный снимок.
Экспорт только читает данные, не импортирует, не удаляет и не изменяет отчёты.

## Будущие уведомления
reportSignals возвращает признаки unusual-outcome и disputed-report с устойчивым ключом на сохранённую ревизию.
Писем, очередей, фоновых задач и записи событий нет. Для доставки позднее нужна отдельно согласованная outbox-таблица,
уникальный event_key, повторные попытки и фиксация отправки. Текущий признак «другое» — повод проверки, не решение о каноне.

## Административный backup
Экспорт отчётов не является резервной копией базы. scripts/backup-database.mjs — отдельная административная команда.
Нужны заранее установленные pg_dump/pg_dumpall совместимой с сервером версии и age. Скрипт их не устанавливает.
Подготовьте существующий каталог вне репозитория и публичный age recipient. Приватный ключ храните отдельно.
Настройте PGSERVICE и PGSERVICEFILE вне репозитория; используйте SSL verify-full и проверенный CA,
а пароль — через защищённый PGPASSFILE или окружение процесса. Не передавайте строки подключения в аргументах,
не записывайте их в Git. Для Supabase используйте доступный административный endpoint/session pooler, не transaction pooler.

План без подключения и файлов:
    node scripts/backup-database.mjs --plan --output ABSOLUTE_EXTERNAL_DIRECTORY --recipient AGE_PUBLIC_RECIPIENT

Реальное создание после подготовки окружения:
    node scripts/backup-database.mjs --run --output ABSOLUTE_EXTERNAL_DIRECTORY --recipient AGE_PUBLIC_RECIPIENT

pg_dump сохраняет схему, данные, политики, триггеры и привилегии в custom-архив; pg_dumpall отдельно сохраняет роли
без паролей. Оба потока сразу шифруются, открытый дамп на диск не пишется. Новая уникальная папка исключает перезапись.
manifest.json создаётся только после успеха обоих процессов и содержит SHA-256 зашифрованных файлов.
Отсутствующий manifest означает незавершённую копию; такие файлы нельзя считать пригодным backup.
Права управляемых ролей Supabase могут ограничивать дамп: ошибка останавливает операцию.
Роли и данные читаются отдельными командами; на время backup не меняйте роли/схему.

Для полноценного восстановления проекта также нужны:
- защищённая копия самих объектов Storage (дамп содержит только метаданные);
- настройки Auth, SMTP, провайдеров, Edge Functions, расширений и отдельное хранилище секретов;
- код приложения соответствующей версии и реестр миграций;
- изолированный тест восстановления с совместимыми расширениями и сопоставлением управляемых ролей.
Встроенный backup/PITR Supabase зависит от тарифа и не заменяет отдельную копию объектов Storage.

Порядок проверки: сверить хэши с manifest, расшифровать потоком age, проверить список pg_restore,
восстановить в отдельный тестовый проект согласно официальной процедуре Supabase, проверить числа строк,
RLS под разными пользователями, функции, Auth и связи Storage. Не запускать восстановление поверх production.
После успешного теста отдельно зафиксировать дату, версию инструментов и результат проверки.
Нужны регулярные копии вне сервера, политика хранения и периодические тесты восстановления;
автоматическое расписание на данном этапе не включено.

Справочники:
- https://supabase.com/docs/guides/platform/backups
- https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore

В этой задаче реальный backup и восстановление не запускались. PostgreSQL CLI и age в доступном PATH не найдены.

## Пробный администратор отчётов
Добавлена область all-drafts и просмотр исходных данных отчётов в раскрывающихся карточках.
Сервер подтверждает постоянный аккаунт через Auth и вызывает is_adventure_report_admin.
Функция читает только членство вызывающего аккаунта в закрытой app_private.adventure_report_admins.
Данные профиля (user_metadata и пользовательские флаги роли) не используются.
Политика RLS разрешает администратору только SELECT всех черновиков. INSERT/UPDATE остаются только для собственного отчёта.
Права на канон, игровые таблицы и редактирование чужого отчёта не выдаются.
Истечение expires_at или удаление назначения закрывает последующие чтения без ожидания обновления JWT.
Уже скачанные файлы и показанные снимки отозвать невозможно.

Порядок применения после отдельного разрешения:
1. 20261117120000_adventure_report_drafts.sql — создание хранилища.
2. 20261118120000_adventure_report_read_admin.sql — закрытый реестр и RLS чтения.
3. Персональное назначение с проверкой постоянного аккаунта и ожидаемого логина.
Персональные UID и назначение не включаются в репозиторий; подготовленный SQL хранится локально вне проекта.
Для пробы предложен срок семь дней. Это срок доступа, а не срок хранения отчётов.
Автотесты проверяют маршруты на моделируемых ответах; проверка SQL/RLS в рабочем проекте описана ниже.
По повторной проверке от 18.11.2026 все три объекта присутствуют.
